# cn-broker-api

把一台 Windows 机器上的**桌面券商客户端**包成一个券商风格的本地 HTTP 接口。

你的策略程序面对的是 `POST /v1/orders`、`GET /v1/positions` 这样的东西，和对接互联网券商
OpenAPI 没有区别。客户端进程在不在、交易登没登、行情断没断、厂商页面被升级冲掉没有——
都是这个服务的事，不再是策略程序的事。

```
       策略程序 ──HTTP──▶ cn-broker-api ──▶ 桌面客户端 ──▶ 券商柜台
     （可移植）           （这个仓库）      （只能在这台机器上）
```

---

## ⚠️ 先读这一段

**这个服务会真的报出委托，也会真的往密码框里打字。** 用之前请确认你接受下面每一条：

1. **它替你输交易密码。** 券商在密码连续输错之后会怎么做（锁多久、要不要人工解锁）
   **各家不同、本项目未核实**。所以服务的默认行为是：**每个账户每天最多提交一次**，
   认不准就中止，**失败绝不重试**。别把 `max_password_submits_per_day` 调大，
   除非你已经向券商确认过策略。
2. **它会修改客户端安装目录里的页面文件**（自动确认那个补丁）。会先备份，但客户端升级
   可能把补丁冲掉——服务把这件事做成一项检查，而不是假设它一直在。
3. **委托是真的。** 没有"演练模式"能让你安心：纸面驱动（`driver.name = "paper"`）压根不连
   客户端，而真驱动一旦受理就是真发出去。
4. **单用户、单机、本机回环。** 服务只监听 `127.0.0.1`，且这一点不可配置——
   这个端口能下单，让它监听外网不该是一个"选项"。

不接受任何一条，就别用。

## 它不做什么

- **不能脱开客户端跑。** 交易能力来自客户端进程自己开的本地端口；没有客户端就没有服务端。
  本服务的定位是**让客户端自己起来并登上**，不是绕开它。
- **不做多账户的界面切换。** 交易登录框里的账号只**核对**、不选择（那个下拉是厂商自绘控件、
  没有窗口句柄）。认错的代价是拿密码去试另一个账号，所以宁可不动手。
- **不做行情研究、不碰数据库、不算因子。** 它只把请求翻译成对客户端的调用。
  依赖表里只有四项，这是刻意的。

## 架构

两层，接缝只有一处：

```
HTTP 层（Flask）              契约 = TradingPort 的投影，与厂商无关
    │
账户亲和串行执行器            一个账户的队列抽干再切下一个
    │
Driver                       ← 唯一与厂商有关的一层
    ├── tdxquant             桌面客户端（进程监护 + 登录 + 页面补丁 + 本地 JSON-RPC）
    ├── paper                不连任何东西（联调 / CI / 分清"契约错还是驱动错"）
    └── …                    换厂商＝加一个驱动，HTTP 层一行不改
```

**桌面监护里，机制是代码、配方是数据**：找窗口、填密码框、按颜色找按钮、量星号总宽这些是
**机制**（与厂商无关）；「要保证哪几个进程在跑、可执行文件相对路径、登录框怎么认、
登上了没有用哪个调用验」是**配方**（每个驱动一份数据）。换一个更精简的客户端版本，
多半是加一份配方，不是写新代码。

## 快速开始

需要 **Windows** + **Python 3.11 以上**（`tomllib` 要标准库自带）。

```bash
git clone <this repo> cn-broker-api
cd cn-broker-api
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
```

配置**放在仓库之外**（见下一节），然后：

```bash
set CN_BROKER_API_CONFIG=D:\path\to\cn-broker-api.toml
.venv\Scripts\python -m cn_broker_api
```

首次启动会在状态目录里生成一个 token 并打印路径。所有接口调用都要带
`Authorization: Bearer <token>`。

先用纸面驱动跑一遍（`driver.name = "paper"`），确认接口通了，再换真驱动。

## 配置

复制 `config.example.toml` 到**仓库之外**，改成你的机器实际情况。默认位置是仓库的上一级
（`../cn-broker-api.toml`，刚好在 git 视野之外），也可以放任意位置然后指环境变量：

```bash
set CN_BROKER_API_CONFIG=D:\path\to\cn-broker-api.toml
```

**「有哪些可配置」有两处权威，都不会和代码分叉：**

1. `config.example.toml` —— 全部配置项都在里面，每项写了用途、默认值、以及那个默认值的由来。
   有一条用例盯着它：**新加了配置项但忘了写进模板，测试会红。**
2. 服务启动时把生效的全部配置打印一遍，在吃默认值的项前面标一个 `~`：

```
    driver.tdxquant.tdx_home                     D:\Common\TDXV2026X64
  ~ watchdog.enabled                             false
```

⭐ 「在吃默认值」必须标出来：**漏写一项**和**写了一项写错值**现象完全不同，
而只看最终值分不出这两种。诊断页上也有同一份清单。

**配置（人写）与状态（机器写）刻意分成两处：**

| | 配置 | 状态 |
|---|---|---|
| 内容 | 端口、客户端装在哪、选哪个驱动、每天最多试几次密码 | 今天提交过几次密码、上次登录结果、健康检查缓存 |
| 格式 | TOML | JSON |
| 谁写 | **只有人** | **只有程序** |
| 手改 | 随时 | 绝不 |

选 TOML 的唯一实际理由是**能写注释**——配置项该说明用途和默认值的由来，而 JSON 做不到。
而 `tomllib` 只能读不能写，这个"缺点"正好把纪律焊死：**服务物理上改不了你的配置**，
手写的注释不会被状态写入冲掉。

🔴 **仓库里不放任何凭据。** `.gitignore` 挡掉了 `*.toml`（只放行示例）、token、state 目录、
以及**截图**（窗口位图会把账号、持仓、资产原样拍进去）。

## 接口

契约是 `TradingPort` 的 HTTP 投影，不是厂商接口的一对一映射。厂商那套有 70 多个函数，
其中公式引擎、往客户端界面写回、我们自有更好来源的财务统计都不投影出来——
**暴露的是要用的，不是能做的**。加一个能力＝加一个端点 + 在 `capabilities` 里加一条。

```
GET    /v1/meta                    契约版本 / 驱动名 / 能力清单 / 版本号
GET    /v1/health                  结构化检查项（缓存 + 年龄，便宜）
POST   /v1/health/refresh          强制重探（要连客户端，只能按需打）
POST   /v1/session/ensure          把客户端弄到「交易通道可用」。幂等、单飞
GET    /v1/jobs/{id}               上一步的进度与终态
GET    /v1/state                   诊断页要的：额度、上次登录、看门狗、当前生效配置
GET    /                           诊断页（单文件，无构建步骤）

POST   /v1/orders                  下单
DELETE /v1/orders/{order_id}       撤单（内部含「撤完再读一次」整段循环）
GET    /v1/orders                  当日全部委托（对账用）
GET    /v1/positions               持仓
GET    /v1/account                 资产
```

### 三处容易做错的口径

**① 查询是三态，不是两态。** 「查不到」和「真的没有」必须分得开：

```json
{"known": true,  "rows": []}            ← 真的空仓 / 今天真的没有委托
{"known": false, "reason": "…"}         ← 判不了
```

把两者揉成一个，症状不是报错——是某天早上对账把持仓账本整表删了、执行侧从零重新建仓。
**传输层失败**（连不上、超时、协议错）才走非 2xx。

**② 委托有中间态，它不是拒单。** 桌面客户端可能把委托推给界面等人确认，那是「结果还没定」，
不是「被拒了」。当拒单处置过一次的代价是：柜台已经全部成交，而我们记成失败。

```
201  真报进柜台了
202  收下了、还没办完  ⇒ 必须重新观测柜台，别拿"我这次调用没成功"当"柜台没收到"
409  定性拒单，原因已知
503  通道不可用（含「补丁不在所以不受理」）
504  状态未知，须熔断对账
```

**③「我发了撤单」与「这笔没成交」是两件事**，中间隔着一场会输的比赛。撤单在服务内部是
「提交 → 重查 → **撤完再读一次、按事实定终态**」的一整段，调用方只看最终事实。

## 看门狗

盯着客户端进程在不在，掉了就拉起来。**默认关**（`watchdog.enabled = false`）——它会真起进程。

它只做一件事，以及刻意不做的三件：

| | |
|---|---|
| **做** | 每隔一会儿枚举一次进程，配方里该在跑而没在跑的，拉起来 |
| **不做①** | **绝不填密码**。交易登录仍然只由 `POST /v1/session/ensure` 触发 |
| **不做②** | **绝不 kill**。只在「进程不存在」时拉起 |
| **不做③** | **一次只拉一个**。两个都缺时先拉主程序，下次醒来再看交易模块 |

每条都有具体理由：

- **不填密码**是因为密码额度每天一次，而看门狗每分钟醒一次——让它去登录，第一次失败就把
  当天额度烧光，而且是在没人看着的时候烧的。⇒ 看门狗保证的是**进程活着**，不是**通道可用**，
  这两件事中间还隔着三道门（客户端行情登录、交易账户登录、自动确认补丁）。
- **不 kill** 是因为进程还活着但没响应时把它杀掉重启，会打断正在飞的委托。
  「没响应」和「没进程」是两件事，看门狗只处理后者。
- **一次只拉一个**是因为客户端还在初始化就又弹一个窗口出来，而登录那侧的第一步是
  「先分类是哪道门」——两道门同时在场正是那一步最容易认错的场面。

还有两个闸：**时段闸**（默认 08:40~15:10、只工作日；半夜三点把客户端拉起来除了弹个窗口没有
任何用）和**每日拉起次数上限**（默认 3；防「起来就自己退」的死循环——那种情况下无限重启只会
刷屏，真正该做的是让人来看一眼）。次数**落盘**，所以重启服务不会把它清零。

⚠️ 时段闸**刻意不判节假日**：本服务不碰数据库、不该有交易日历这个依赖。节假日多起一次客户端的
代价是桌面上多一个窗口；引一份日历进来的代价是给这个只该说 HTTP 的服务加一个数据依赖。

## 部署

**不能做 Windows 服务，也不能进容器**：这个服务要枚举窗口、往密码框里打字、抓窗口位图，
而 Windows 服务跑在会话 0、容器里根本看不到桌面。它必须跑在**交互桌面会话**里。

⇒ 用**登录时触发的计划任务**：

```powershell
powershell -ExecutionPolicy Bypass -File .\install_task.ps1 -ConfigPath D:\path\to\cn-broker-api.toml -Start
powershell -ExecutionPolicy Bypass -File .\install_task.ps1 -Uninstall
```

为什么是计划任务而不是启动文件夹：计划任务有「上次运行结果」这一栏（配置写错了退出码就是 2，
一眼能看见）、能用 `schtasks /run` 手动触发一次，也不会被谁清理开始菜单时顺手带走。

脚本里三处是有讲究的：

- **不勾「以最高权限运行」**。目标客户端是非提权进程，往它的窗口发消息不需要提权
  （提权只在反方向才是必需的）；而提权跑的话，本服务启动的客户端会继承高完整性级别，
  与人平时手动启动的那一份不是同一套环境。
- **`LogonType Interactive`**。勾成「不管用户是否登录都运行」会把它扔进会话 0，
  那里没有桌面、没有窗口，整套 Win32 自动化一个动作都做不成。
- **装之前先把配置读一遍**。任务里跑的是 `pythonw.exe`（登录时不该弹黑框），
  而 `pythonw` 没有控制台 ⇒ 配置错误那行 stderr 会被丢掉，能看见的只有「上次运行结果 = 2」。
  所以安装脚本先用带控制台的解释器验一次，让错误现在就以人话的形式出现。

⭐ 分工：**计划任务保证本服务活着，看门狗保证客户端活着。** 两层各管一层。

**部署 = `git pull` + 重启。** 没有编译、没有打包、没有安装器——"随时能改"在引入打包器的
那一刻就死了。随时重启是安全的：额度都落盘、`/v1/session/ensure` 幂等。

⚠️ **刻意不声明 DPI 感知**：客户端是 DPI 不感知进程，本服务保持不感知，`GetWindowRect`、
`PrintWindow` 位图、我们 Post 的客户区坐标才落在同一套坐标里。

## 几条反直觉的设计取舍

**「受理即真发出」。** 自动确认补丁不在、配置关着、时间窗没覆盖当前时刻——这些情况下服务
一律**拒绝受理**（503），而不是受理完让委托躺在客户端队列里等人点。所以调用方连"补丁"
这个词都不需要知道。

**健康检查必须便宜。** 「交易账号登录了没」这一项要连客户端、查一次资产，几秒钟。
诊断页每几秒刷一次的话，不缓存等于整天骚扰交易通道 ⇒ `GET /v1/health` 给**缓存 + 年龄**，
`POST /v1/health/refresh` 才真去探。页面上必须显示"数据于 N 秒前"——静默展示旧数据的状态页
比没有更糟。

**行情通不通，判的是「答不答话」而不是「有没有现价」。** 集合竞价还没撮合时现价本来就是 0；
把它一律判红的结果是每天早上一次假警报，而**假警报比不探更糟**——人会学着无视整条自检。
所以「现价为 0」只在连续竞价时段内判红。

**登录是状态驱动，不是弹框驱动。** 循环是「已登上？→ 有框？→ 处理」，因此天生幂等，
定时任务可以放心反复打。写成「等登录框」会把「本来就好了」读成超时失败。

**不做自动回落。** 一个通道失败了不去偷偷试另一个：两条通道的故障表现完全不同，
自动回落会把"服务挂了"伪装成"柜台拒单"。

**日闩落盘，密码只在内存。** 两者刻意反向——**前者怕丢掉**（放内存的话重启就清零，
"重启三次＝无声无息地试了三次密码"），**后者怕留下来**。

## 开发

```bash
.venv\Scripts\python -m pytest -q
```

跟客户端有关的用例按平台跳过，所以在 Linux 上也能跑（CI 用纸面驱动）。

**改动纪律**：`drivers/tdxquant/login.py`、`health.py`、`autoconfirm.py` 是从生产环境
**整文件搬过来**的，里面每一处 `⭐`/`🔴` 注释都对应一次真实故障。要动它们之前先读那些注释；
不要为了"看起来更整洁"重排这些代码——那等于把真机验证的结果作废。
